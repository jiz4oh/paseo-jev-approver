# Plugin localization

The plugin follows the active Paseo UI language via the host document's `lang` attribute where available, falling back to the browser/device locale. English (`en`) and Simplified Chinese (`zh-CN`) are translated; other Paseo locales currently use English fallback. The original approval prompt and all model IDs remain unchanged (only UI strings are localized).

## Updating UI text

1. Replace user-visible UI literals in `client/**/*.tsx` with `t("English source string")` obtained from `usePluginT()`.
2. Add the exact source string to `client/locales/en.json`, with itself as the value.
3. Add the matching key and its translation to **every other JSON catalog** in `client/locales/`.
4. Run `npm run i18n:check` (also run as part of `npm run check` in pull-request CI).

The gate rejects missing, obsolete and empty translations, unknown static `t()` keys, literal JSX labels and simple hard-coded text children. Complex constructed user-visible strings and registration-time labels still require code review. When adding a new locale, add its catalog using the same keys; English is the fallback. Dynamic server-generated `reason`, `detail`, and `nextStep` fields are not translated because they are model/daemon output, not UI copy.

**Note:** The settings-screen and history-screen navigation titles are registered once when Paseo loads the plugin. Paseo's current public plugin SDK does not document an on-language-change registration API; their route headers may keep their initial labels until the plugin is reloaded. Web screen content follows changes to the document language attribute. Because the current public plugin SDK does not expose Paseo's selected locale, changing the app language without updating the document attribute may not update plugin content; native clients use a device-locale fallback.
